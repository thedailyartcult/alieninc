Multi-Tenancy & Workspaces

CMB natively supports multiple workspaces — each is an isolated tenant with its own memories, sessions, and receipts. Recall never crosses workspace boundaries, so subsidiary companies can share the same deployment without shared context.

The Model

  • Tenant = workspace. The trust boundary. Subsidiaries get their own workspace (alieninc, default, operations, …).
  • Project = repo inside a workspace. Optional refinement, not a boundary.
  • Isolation is server-enforced. A workspace never sees another's memories.
  • Sharing = curated read-only copy. A memory is materialized in the target workspace with source=shared_from:<ws>:<id> provenance. Owner's version always wins; copies are never mutated in place.
Sharing rule: never share PII, secrets, or client data. Share structural and decision knowledge only. Secrets (credentials, tokens) are hard-blocked.

Sharing a Memory (v1 recipe)

Cross-workspace sharing is a curated read-only copy with provenance. The source workspace keeps ownership; the target workspace gets a copy tagged shared_from. Revoking = deleting the copy.

Share

cmb_remember(
  workspace="<target>",
  repo="<target repo>",
  title="nginx config — shared from alieninc",
  content="<the memory content>",
  metadata={ "shared_from": "alieninc:<source_memory_id>", "shared_sync": true }
)

Find shared copies

cmb_recall(query="nginx", workspace="<target>")
# copies carry metadata.shared_from = "<source_ws>:<id>"

Revoke / update

cmb_forget(memory_id="<copy_id>", workspace="<target>")   # revoke
# update: owner edits the source; re-share to push the new copy (owner version wins)

Default Workspace Selector

Every MCP connection can be pinned to a tenant via the CMB_DEFAULT_WORKSPACE environment variable. The wrapper injects it as the default workspace argument on any tool call that accepts one — an explicit per-call workspace always wins. 

# opencode.jsonc → mcp.cmb.environment
{
  "CMB_DB_PATH": "/srv/cmb/data/cmb.db",
  "CMB_API_TOKEN": "…",
  "CMB_DEFAULT_WORKSPACE": "alieninc"
}

Managing Workspaces

From admin → CMB → Workspaces (admin.html) or the engine API directly:

EndpointPurpose
GET /api/workspacesList all workspaces (name, memories, description, visibility, repos).
POST /api/workspaces/createCreate {workspace, description, visibility, confirmed}.
POST /api/workspaces/rename{workspace, new_name}
POST /api/workspaces/describe{workspace, description}
POST /api/workspaces/visibility{workspace, visibility, confirmed} — personal/shared.
POST /api/workspaces/copyDuplicate a workspace {workspace, new_name?}.
POST /api/workspaces/delete{workspace} — destroys the tenant and its memories.
POST /api/workspaces/merge{source, target} — merge one workspace into another.

Workspace-Aware Tools

Most cmb_* tools accept a workspace parameter: cmb_start_session, cmb_remember, cmb_recall*, cmb_ingest, cmb_context_savings, cmb_stats, and the governance tools. When the wrapper selector is configured, callers never need to repeat the workspace.

Deploying a Subsidiary

  1. Create the tenant: POST /api/workspaces/create (e.g. centra).
  2. Point that team's AI tool at CMB with CMB_DEFAULT_WORKSPACE=centra.
  3. Verify isolation: cmb_recall from centra must never return alieninc memories.
  4. Share curated knowledge on demand (read-only copies with provenance).
