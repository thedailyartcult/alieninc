Economics

How CMB Reduces Token Usage

The core problem: an AI agent re-reading the same files, docs, and transcripts every session burns tokens on context it already has. CMB replaces that with stored summaries recalled under a hard token budget.

The Mechanism

  1. Store once. Files, API structures, and decisions are distilled into durable memories.
  2. Recall on demand. cmb_recall_context(query, token_budget=512) packs only the relevant memories into ≤512 tokens — instead of dumping a full file into context.
  3. Hand off. Session end writes a compact summary + open threads; the next session starts with that context injected, not a full transcript resume.

Running average: across measured recall receipts, CMB is tracking ~35% token savings, with individual calls between 40–66%. The goal is 50–80% once recall-before-read discipline is fully adopted on every session.

What Saves the Most

  • File-structure memories — one 512-token recall replaces a multi-thousand-token file read.
  • Architecture decisions — no re-litigating settled choices in later sessions.
  • Bug cause → fix pairs — the fix is one recall away, not a re-investigation.
  • Session handoffs — replace 450K-token transcript resumes with a compact summary.

Monitoring

Every recall appends a content-free, hash-chained receipt. CMB aggregates them into a savings report, so savings are measurable, not vibes.

cmb_context_savings(workspace="alieninc", repo="backend")
# → total saved tokens, savings ratio, per-operation breakdown

Rules of Thumb

  • Always use cmb_recall_context with the smallest sufficient budget.
  • Check CMB before reading any file (tool.execute.before does this automatically).
  • Store summaries, not full file contents.
  • Never store credentials, secrets, or raw logs.
